# 01 · Navigation 设计目的与需求

> 本文定义 Navigation 的问题边界、功能/非功能需求和设计追溯。
> 设计契约见 [04-design.md](04-design.md)，实现架构见 [02-architecture.md](02-architecture.md)，
> 验收映射见 [08-acceptance.md](08-acceptance.md)，实施 TODO/闭环见 [13-todo.md](13-todo.md)。

## 一、设计目的：解决什么问题

### 1.1 核心矛盾

Navigation 的存在，是为了调和移动机器人导航中的五组结构性矛盾：

| 矛盾 | 传统方案的问题 | Navigation 的回应 |
| --- | --- | --- |
| 无地图 vs 要导航 | Nav2 依赖全局/局部代价地图，建图成本高、维护复杂，动态环境地图易失效 | 用位姿索引的深度关键帧集合替代显式地图，记忆随空间覆盖增长而非运行时长 |
| 端到端策略 vs 安全不可协商 | 学习型策略存在长尾失效，黑箱输出不能直接驱动底盘 | 三级安全链独立进程，拥有最终否决权，策略输出永远不直达底盘 |
| 研究代码 vs 工程可部署 | VNTPA 等论文代码是训练脚本，缺少心跳、诊断、降级、恢复 | Component + Runner 双层，Runner 可单测，Component 接 autolink 生态 |
| 底盘多样性 vs 固定算法假设 | 差速/全向/阿克曼/足式的运动学差异硬编码在算法里 | `PlatformProfile` 契约，速度/加速度/jerk/足迹约束统一读取，换底盘改配置 |
| 家具场景感知盲区 vs 深度相机局限 | 透明玻璃、低矮障碍、反光表面使深度图“看起来空旷” | 感知可信度场，不可信区域视为潜在障碍，CBF 在“不知道”处保守 |

### 1.2 一句话目的

让端到端策略（VNTPA）能在真实移动机器人上安全、可维护、可替换地完成无地图导航，
同时不牺牲工程可部署性。

### 1.3 不是什么

| 不做 | 原因 |
| --- | --- |
| 不做 SLAM | `map→odom` 由 Atlas 维护，Navigation 只消费位姿，不重复造轮子 |
| 不做地图构建 | 空间记忆是策略推理的上下文，不是全局一致性地图 |
| 不做底层控制 | 输出 Twist 给底盘，不涉及电机控制、PID 调参 |
| 不做多机协同 | 单机导航系统，多机调度是上层任务层的事 |
| 不做训练框架 | `tools/vntpa/` 是离线 Python 工具，不参与 C++ 核心库构建 |
| 不做通用规划器 | 不替代 Nav2 的几何规划能力，VNTPA 与 Nav2 是同级可选项 |

## 二、功能需求

### 2.1 导航能力

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| F-01 | 点目标导航：给定 `GoalSpec.pose` 或 `/navigate_to_pose` Action，到达指定位姿 | 闭环仿真中距目标 < 0.3 m |
| F-02 | 探索：无目标时主动探索未知区域，建立空间记忆 | 前沿消失或覆盖率达阈值 |
| F-03 | 跟随：跟随持续移动的目标，保持距离 | 距离保持在 [1.0, 3.0] m 区间 |
| F-04 | 区域覆盖：对指定多边形区域做全覆盖 | 覆盖率 > 95% |
| F-05 | 门通过：检测门框、对齐、穿门 | 通过后距门框 > 1 m |
| F-06 | 电梯乘降：跨楼层导航的电梯部分 | 完成六阶段状态机 |
| F-07 | 窄通道通过：宽度接近体宽时安全通过 | 无碰撞通过，速度 < 0.2 m/s |
| F-08 | 动态避障：近场障碍毫秒级响应 | 反射层延迟 P99 < 30 ms |

### 2.2 决策能力

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| F-09 | 长距离导航：空间记忆不随历史长度退化 | 1000 m² 场景 1 小时运行，条目数增长与空间覆盖相关 |
| F-10 | 跨传感器泛化：RealSense / Kinect / ZED 开箱即用 | 切换传感器不改代码 |
| F-11 | 模型可替换：切换 `policy.name` 不触碰主循环 | 除 `planning/plugins/policy/` 外零改动 |
| F-12 | 底盘可替换：切换 `kinematic_type` 不触碰算法 | 除 `conf/navigation.pb.txt` 外零改动 |
| F-13 | 场景可替换：`GoalSpec.type` 变化时自动切换场景 | 无优先级栈，纯映射表 |
| F-14 | 多策略仲裁：VNTPA 与 Nav2 控制器同级竞争 | 窄通道场景自动选几何规划器 |

### 2.3 安全能力

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| F-15 | 三级安全链：仲裁 → CBF 投影 → 可行性过滤 | 每级可独立测试 |
| F-16 | 零速兜底：任何一级故障输出零速 | 故障注入测试通过 |
| F-17 | 感知可信度膨胀：透明/低矮障碍的“不知道”区域视为潜在障碍 | 碰撞率为零 |
| F-18 | 恢复机制：语义归因后选择恢复动作，不盲目 Spin/ClearCostmap | 家具场景脱困率 > 80% |
| F-19 | AEB 自适应：TTC 阈值随速度变化 | `τ = t_react + v/(2a_max)` |

### 2.4 系统能力

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| F-20 | 心跳监控：每个进程必须有心跳，静默失效不可接受 | 心跳超时触发降级 |
| F-21 | 故障分类：瞬时/持久/致命三级分类 | 分类边界正确 |
| F-22 | 自动降级：policy 失效切反射模式，safety 失联紧急停车 | 进程卡死注入测试通过 |
| F-23 | 诊断上报：标准化 `DiagnosticReport` | 每模块上报最低指标集 |
| F-24 | 故障注入：六类场景可重复注入 | 全部进入预期降级状态 |
| F-25 | 位姿契约门禁：TF 不满足时拒绝启动 | `map→camera_optical_frame` 不可查时 `Init()` 返回 false |

### 2.5 交互能力

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| F-26 | 点击选目标：像素 + 深度 + 内参 → 3D 坐标 | 深度无效时拒绝并提示 |
| F-27 | 语言指令：自然语言 → `GoalSpec.semantic` | 无法落地时返回澄清请求 |
| F-28 | 语义搜索：开放词汇查询（“沙发上的杯子”） | 场景图返回候选并闭环 |

## 三、非功能需求

### 3.1 性能

| 编号 | 需求 | 指标 | 验证方式 |
| --- | --- | --- | --- |
| N-01 | 反射层延迟 | P99 < 30 ms | `ReactiveAvoider` 基准 |
| N-02 | 安全链硬截止 | 50 ms，超时率 0 | 看门狗计数 |
| N-03 | 关键帧过滤 | P99 < 2 ms | `KeyframeFilter::TryAccept` 基准 |
| N-04 | CBF 投影 | P99 < 1 ms | `CbfFilter::Solve` 基准 |
| N-05 | 动作块融合 | < 100 μs | `ChunkBlender::Consume` 基准 |
| N-06 | 热路径零堆分配 | 无 new/delete | heaptrack 验证 |
| N-07 | 端到端延迟预算 | 感知 + 推理 + 护盾 < 100 ms | 峰值负载测试 |

### 3.2 安全

| 编号 | 需求 | 指标 |
| --- | --- | --- |
| N-08 | 安全层故障域隔离 | 独立进程，`-fno-exceptions -fno-rtti` |
| N-09 | 安全层 fail-safe | 传感器失效默认零速，非透传 |
| N-10 | 决策层异常不越界 | 模块边界转 `StatusOr` |
| N-11 | 学习型输出不可信 | 策略输出必经三级安全链 |
| N-12 | 反射优先于全局 | 近场有风险时覆盖策略方向 |

### 3.3 可维护性

| 编号 | 需求 | 指标 |
| --- | --- | --- |
| N-13 | 一文件一类 | 每个 `.hpp` 一个主 class |
| N-14 | 文件名 ≤ 4 单词 | 超限用登记缩写 |
| N-15 | 每个类可单测 | perception/memory/planning/safety 均可用 mock 单测 |
| N-16 | 依赖单向无环 | common 是根，模块互不反向依赖 |
| N-17 | 插件差异收敛在适配器 | 模型差异不渗透到 app/behavior/safety |

### 3.4 技术约束

| 编号 | 约束 | 指标 |
| --- | --- | --- |
| N-18 | 技术基线 | C++17、CMake ≥ 3.22.1、Protobuf 3 |
| N-19 | 消息来源 | automsgs 提供基础消息，navigation 只定义 5 个自定义 proto |
| N-20 | 模型推理 | 经 `autonomy::common::network::Engine`，后端可切换 |
| N-21 | 公共宏 | `autonomy/common/macros.hpp`，不自定义 |
| N-22 | 代码风格 | 对齐 `context.hpp`：`#pragma once`、4 空格、函数体左括号独占一行 |
| N-23 | 配置文件 | 单一 `navigation.pb.txt`，三份 DAG 共读 |
| N-24 | DAG 数量 | 3 份：navigation / safety / guardian |

> 注：原需求稿写“4 个自定义 proto”；当前代码为 5 个
> （observation/navigation/lifecycle/config/plugins），以 N-19 的 5 个为准。

### 3.5 可测试性

| 编号 | 需求 | 指标 |
| --- | --- | --- |
| N-25 | 无泄漏无数据竞争 | `-fsanitize=address,thread` 通过 |
| N-26 | 闭环评测 | 含动态障碍、传感器退化、SLAM 失效、目标不可达 |
| N-27 | 故障注入全覆盖 | 六类注入场景有自动化测试 |
| N-28 | 单测覆盖率 | 核心类单测覆盖 |

## 六、一句话

Navigation 的设计目的是让 VNTPA 这类端到端策略能在真实移动机器人上安全、可维护、
可替换地完成无地图导航。它通过位姿索引记忆替代地图、三级安全链独立进程、
Component + Runner 双层、`PlatformProfile` 底盘契约、感知可信度场，调和了
“无地图 vs 要导航”“端到端 vs 安全”“研究 vs 工程”“底盘多样 vs 固定假设”
“感知盲区 vs 深度局限”五组矛盾。28 条功能需求和 28 条非功能需求逐条可追溯到
设计决策，按 P0–P6 分阶段实施，每条需求都有明确的验收标准。
